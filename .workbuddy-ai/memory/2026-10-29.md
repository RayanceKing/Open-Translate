# 2026-10-29

## Open Translate 0.2.0：设置页 + 多引擎重构

**背景**：项目原为 140 行左右的极简双语翻译工具（Tampermonkey 脚本 + MV3 扩展）。需求是补齐类似 immersive-translate 旧版设置页，支持切换翻译引擎、双语显示样式、AI Token 填写。

**架构决策**
- 设置统一为一个 `settings` 对象存 `chrome.storage.local`（脚本用 GM 存储），默认值/合并/归一化集中在 `extension/lib/defaults.js`，扩展与脚本各维护一份等价 DEFAULTS（content script 不能用 ES module）。
- 引擎抽象为 `lib/engines.js` 的 `translateTexts({engine, texts, source, target, config}) -> string[]`，支持批量；AI 引擎（openai/deepseek/gemini/claude）走编号批量 + 解析失败自动降级为逐段请求。
- 脱敏在 background 集中处理（`lib/privacy.js`），content 只负责文本抽取与渲染。
- AI 的 prompt/glossary/temperature 放在全局 `settings.ai`，引擎配置只留 key/baseUrl/model，避免设置页出现四套重复表单。
- 三种显示模式：bilingual（兄弟节点插入）、translation（清空元素 innerHTML 并记录原 HTML 以便还原）、hover（默认隐藏 + JS mouseenter 显示）。LI/TD/TH/DD/DT/BLOCKQUOTE 追加到元素内部以保留缩进。

**文件**
- 新增 `extension/lib/{defaults,engines,catalog,privacy,store}.js`
- 新增 `extension/options.{html,css,js}`（左侧导航 + 7 个分区 + 实时预览 + 导入导出 + 主题切换）
- 新增 `extension/popup.css`，重写 popup/background/content
- 重写 `tampermonkey/open-translate.user.js`：Shadow DOM 内嵌设置面板（通用/样式/引擎/AI 四个 tab），同样 9 个引擎
- README 全面更新

## 悬浮球（Immersive Translate 风格）

- 原右下角横条 `.ot-panel` 全部换成 44px 圆球 `.ot-dock` + 悬停展开的 `.ot-menu`（绝对定位在球的左/右侧，不占布局宽度，球的位置不会随引擎名长短漂移）。
- 拖动：pointerdown/move/up + setPointerCapture；移动超过 4px 才算拖拽。**切换逻辑放在 click 里，拖拽结束后 350ms 内用 suppressClick 吞掉紧随其后的 click**，否则松手会误触发翻译。
- 吸附：松手按球心与视口中线比较决定 left/right，`left = 10` 或 `innerWidth - 54`，top 存成 0–1 比例，随 `settings.ui.dock = {side, top}` 持久化；resize 时重新计算。
- 位置写入会触发 `chrome.storage.onChanged`，content script 用 `dockWriteAt` 时间戳（600ms 内忽略）避免自己写的变更触发"重新翻译整页"。

## 严重 bug（已修）：油猴脚本 TDZ 崩溃

`let settings = loadSettings()` 写在文件顶部，而 `loadSettings` 内部会调用 `deepMerge` → `isPlainObject`（`const` 声明在更后面）。首次安装时 GM_getValue 返回 null 不触发合并，所以测试没暴露；**一旦用户保存过设置，再次加载就会抛 `Cannot access 'isPlainObject' before initialization`，整个脚本挂掉**。修法：把初始化挪到合并函数定义之后，并在注释里说明原因。
教训：给 userscript 做 stub 测试时，必须同时覆盖"无存储"和"有存储"两条分支，只测 `GM_getValue = (k,d) => d` 会漏掉这类初始化顺序问题。

## 悬浮球最终形态（用户反馈后调整）

用户嫌横向胶囊菜单（翻译此页 / 引擎名 / ⚙）冗余，改为**竖向堆叠**：32px 齿轮圆钮在上、44px 翻译球在下，间距 6px，整组一起拖动吸附。横向 `.ot-menu` 相关 CSS/JS 已全部删除，引擎名改放到齿轮的 `title` 里（`设置 · 当前引擎：Google`）。

## Microsoft 翻译改为免费优先（Bing 公开通道）

**动机**：用户质疑「为什么微软翻译要填密钥，immersive-translate 里不是免费的吗」。确实，早期沉浸式翻译的微软通道就是免费的，只有 Azure 订阅才需要 key。

**实现**（`extension/lib/engines.js` + userscript 同名函数）
1. `GET https://www.bing.com/translator`（会 302 到 `cn.bing.com`，所以 host 必须从 `response.url` 取 origin，不能写死）。
2. 正则抓三样：`IG:"([0-9A-Fa-f]+)"`、`data-iid="([^"]+)"`、`params_AbusePreventionHelper\s*=\s*\[\s*(\d+)\s*,\s*"([^"]+)"\s*,\s*(\d+)` → key / token。
3. `POST {host}/ttranslatev3?isVertical=1&IG=..&IID=..`，body 是 `fromLang=auto-detect&to=..&text=..&token=..&key=..`。
4. 凭证缓存 8 分钟；401/403 时清缓存、重新抓一次并重试（`error.retryable`）。逐段请求，因为该端点一次只吃一段文本。
5. `settings.engines.microsoft = { useKey:false, key:'', region:'global' }`，`useKey` 为 false 走免费，true 走 `api.cognitive.microsofttranslator.com`。

**关键坑：缺 User-Agent 会返回 401 `{"ShowCaptcha":false}`**
Node 的 fetch 默认不带浏览器 UA，所以本地测试一开始「凭证已过期」，看起来像 token 抓错了。做了请求头矩阵实验才定位：
- 无 UA 无 cookie → 401
- 只有 UA（Chrome 或 Safari 任意）→ **200**
- 只有 Referer / 只有 Accept-Language / 只有 cookie → 401
所以 UA 是唯一硬性条件，cookie 可有可无。浏览器里 fetch 会自动带真实 UA（禁止手动设置，设了也会被静默忽略），因此浏览器环境本来就正常；显式写 `BROWSER_HEADERS` 只是为了 Node 下能自测。另外 `https://edge.microsoft.com/translate/auth` 已 404，那条老路子彻底失效，别再试。

**旧配置迁移**：0.2.0 之前 microsoft 只有 `{key, region}` 没有 `useKey`，直接合并默认值会让填过 key 的用户静默掉回免费通道。修法是在 `normalizeSettings` / `loadSettings` 里检查**原始存储对象**（不是合并后的结果，因为合并后 `useKey` 已被默认值填成 false）：`useKey === undefined && key 非空 → useKey = true`。

**设置页条件字段**：catalog 的 field 加 `dependsOn: 'useKey'`，渲染时若依赖未勾选就加 `hidden`；勾选变化时 `syncServiceDeps(card)`（扩展）/ `syncFieldDeps()`（脚本）重算 `field.hidden`。注意 userscript 面板只渲染当前选中引擎的字段（`ENGINE_FIELDS[engine]`），且用 `data-k="engines.<id>.<key>"` 定位，不是 id。

## 无头浏览器验证的两个新教训

- **`file://` 下 ES module 直接被 CORS 拦掉**，页面会「渲染出骨架但列表全空」，很容易误判成 JS 报错。必须 `python3 -m http.server` 起本地服务再截图。
- **主题切换有竞态**：`applyTheme()` 会在每次保存后按 `settings.ui.theme` 重新执行，harness 里一次性设 `dataset.theme='light'` 会被它改回去，表现为「卡片是浅色、按钮却是深色」的诡异截图。改成 200ms 间隔反复断言即可。
- 想截长页面的某个区块，别用 `scrollIntoView`（无头下会截到重绘残影，整页错位），改成在 harness 里 `remove()` 掉前面的卡片，让目标自然落在首屏。

## 翻译缓存改为会话级（用户要求「翻译结果要暂时缓存」）

**原实现的真问题**：缓存是 `background.js` 里一个模块级 `Map`。MV3 的 service worker 空闲约 30 秒就被回收，模块状态随之清空——用户切个标签页回来、或页面刷新，缓存就没了，整页重译。

**方案：双层 + 「暂时」语义**
- L1：SW 内的 `Map`，命中零开销。
- L2：`chrome.storage.session`（Chrome 102+）。它**只存在内存、不落盘**，SW 重启保留，浏览器关闭即消失——正好就是「暂时缓存」该有的生命周期，比 `storage.local` + TTL 更干净。
- 脚本版用 `sessionStorage`（同标签页刷新保留，关标签页清空）。
- 另有 TTL 12 小时 + 上限 2000 条，避免浏览器几天不关时长期供应陈旧译文。

**关键实现细节（`extension/lib/cache.js`）**
- **key 用指纹而不是原文**：`engine|target|source|saltFingerprint|textFingerprint`，64 位双 FNV-1a。好处是缓存里根本不存在原文，翻存储也看不出用户读过什么；顺带体积小。
- **salt 承载「改变译文但不改变原文」的因素**：AI 引擎时为 `prompt + glossary + temperature`。原实现的 key 只有 `engine|target|text`，**改了提示词或术语表还会命中旧译文**，这是个真 bug，一并修掉。
- **hydrate 必须并发安全**：`writeCache` 是同步的，而 L2 读取是异步的。若先写后读，flush 会用不完整的 Map 覆盖已有缓存。做法是 `hydrating` 缓存同一个 promise，且 `flush()` 开头先 `await hydrate()`，load 时用 `if (memory.has(key)) continue` 避免覆盖刚写入的新值。
- 落盘 400ms 防抖；`storage.session` 超配额时丢一半重试一次，失败就退回纯内存。
- LRU 用 Map 天然保序：命中时 `delete` 再 `set` 移回队尾。

**验证方式（可复用）**
- `cache.js` 单测：用假 `chrome.storage.session` 共享一个对象，再 `import('./cache2.mjs')` 导入**同一份文件的副本**拿到全新模块实例——等价于 SW 重启（L1 空、L2 有数据），12 项断言全过。
- `background.js` 集成测试：stub `chrome.storage`/`runtime.onMessage`/`fetch`，直接调用捕获到的 listener，用 fetch 调用次数判断命中：首翻 2 次、重翻 2 次（+0）、换语言 4 次（+2）、混合 5 次（+1）。
- 脚本版在浏览器里用 `GM_xmlhttpRequest` 计数 stub：首翻 3 次请求，还原后再翻仍是 3 次。

**入口**：设置页「隐私与安全 → 翻译缓存」（显示条数 + 清空按钮，走 `cache-stats` / `clear-cache` 消息）；脚本面板「通用 → 翻译缓存」。`test-engine` 走的是 `translateTexts` 而非 `handleTranslate`，所以测试连接的样句不会污染缓存。



## 视频双语字幕（0.3.0，对齐沉浸式翻译的核心能力）

**需求**：实现沉浸式翻译的视频双语字幕。这不是「翻译网页文本」的延伸——字幕有自己的时间轴、自己的渲染层，必须独立做。

**三条字幕来源，归一到同一个 cue 列表**
1. `video.textTracks`：浏览器已经把 `<track>` 解析好了，`track.mode = 'hidden'` 即可拿到 `cues` 且不显示原生字幕。零网络开销，优先用。
2. 抓 `<track src>` 自己解析 WebVTT：textTracks 首次读取时 `cues` 往往还是空的（异步加载），所以实际第一次都会走到这条路。
3. YouTube：从 `#movie_player.getPlayerResponse()`（回退 `window.ytInitialPlayerResponse`）取 `captions.playerCaptionsTracklistRenderer.captionTracks`，给 baseUrl 追加 `&fmt=json3` 拉取。**baseUrl 已带查询串，必须判断用 `?` 还是 `&`**。

**选轨策略**：`kind !== 'asr'` 人工字幕 +4 分，匹配 `sourceLanguage` +8 分，auto 时英文 +1。宁可要人工外语字幕，也不要自动生成的本语言字幕。

**渲染**：自绘覆盖层 `position: fixed`，不用 `absolute`——不依赖父元素定位，全屏时照样对齐。位置每次按 `getBoundingClientRect()` 重算：`bottom = innerHeight - rect.bottom + rect.height * position%`。字号按视频高度缩放 `clamp(h*0.042, 14, 44) * 用户百分比`，360px 嵌入到 4K 全屏都可读。

**同步**：rAF 循环只在播放时跑（`play` 起、`pause` 停），暂停时补一次渲染。`findCueIndex` 二分找起点后回看 2 条，处理重叠字幕。

**按需翻译**：只翻当前 ±窗口（前 2 条、后 12 条），播到哪翻到哪，不会把整部视频一次性发出去。cue 的 `translation` 用 `null` 表示「未翻译」、空字符串表示「翻过了但是空的」——否则引擎返回空串会触发无限重试。

**踩到的真 bug**：拖进度条落到无字幕区间时，旧字幕不消失。原因是 `onSeek` 先把 `SUB_STATE.index = -1` 再调 `updateCue()`，而 `updateCue` 用 `index === SUB_STATE.index` 判断是否需要重绘——`-1 === -1` 直接 return。改成 `updateCue(true)` 强制重绘，别再手动改 index。

**YouTube SPA**：监听 `yt-navigate-finish`，换视频后 `stopSubtitles()` + `startSubtitles()` 重新取轨。

**原生字幕冲突**：`html.ot-sub-on .ytp-caption-window-container { display: none }`——双语层已经含原文，原生层只会重复。

**验证方式（可复用，这次的关键技巧）**
无头模式下媒体解码 + `--virtual-time-budget` 不可靠，`video.currentTime` 和 `seeked` 事件不会按预期推进。解法是**用 `Object.defineProperty` 在 video 实例上覆盖 `currentTime` 的 getter**，然后用 `dispatchEvent(new Event('seeked'))` 驱动时间轴，完全绕开真实解码：
```js
Object.defineProperty(video, 'currentTime', { configurable: true, get: () => fakeTime, set: v => { fakeTime = v; } });
```
另外 `play` 事件不冒泡，但 `document` 上的**捕获阶段监听照样能收到**，所以 `video.dispatchEvent(new Event('play'))` 足以触发自动加载。
- 解析器单测：用 `indexOf` 从 content.js 里**切片出真实函数源码**再 `new Function` 执行，避免测试副本与实现漂移。25 项断言覆盖 NOTE 块、内联标签、逗号小数、实体、多行 cue、空 payload、二分边界。
- 端到端：本地 `ffmpeg` 造 14 秒 VP9 视频 + 3 条 cue 的 VTT，断言 t=1/5/9 的原文与译文、t=13 无字幕时隐藏、请求次数、图层唯一、定位像素值（bottom 205px / left 126px 与手算一致）。

**用户脚本差异**：`http()` 走 GM_xmlhttpRequest，VTT 返回字符串、json3 返回对象，靠 `typeof` 分流。面板新增「字幕」tab；`.seg button` 监听必须收窄成 `.seg button[data-mode]`，否则字幕 pane 复用的同款 seg 会把 `displayMode` 写成 undefined。输入框要写 `type="text"`——UI_CSS 用的是 `.field input[type=text]` 属性选择器，缺省 type 匹配不到，深色主题下会露出白底。



## YouTube 上 UI 全废：Trusted Types（用户报「悬浮按钮消失、设置页打不开，但快捷键能用」）

**症状的启示**：快捷键能用、UI 不出现，说明「翻译逻辑活着，UI 构建死了」。这两条路径唯一的区别是——UI 用 `innerHTML` 拼字符串，快捷键不碰 DOM 构建。顺着这条线才找到根因。

**根因**：YouTube 响应头带 `Content-Security-Policy: require-trusted-types-for 'script'`。页面主世界里执行 `element.innerHTML = "<markup>"` 会**抛异常**（不是静默忽略）：
```
TypeError: Failed to set the 'innerHTML' property on 'Element': This document requires 'TrustedHTML' assignment.
```
脚本版（Tampermonkey）跑在页面主世界，`buildUi()` 在 `dock.innerHTML` 处中断：host 元素已 append 进 DOM，但里面的悬浮球根本没生成——所以「看得见容器不存在，球消失」。设置面板同理打不开。扩展的内容脚本跑在隔离世界，本来就豁免页面 CSP，所以扩展没报这个问题。

**修法**
- 建 policy 一次：`window.trustedTypes?.createPolicy('open-translate', { createHTML: m => m })`。**必须 try/catch**——站点若已占用同名 policy，`createPolicy` 会抛 `TypeError`。
- 统一走 `trustedHtml(markup)` 包装，无 policy 时原样返回字符串（普通页面/老浏览器不受影响）。
- 用户可控插值（`ai.prompt`、`ai.glossary`、`subtitles.shortcut`、引擎字段 value）改走 `escapeHtml()`——有了 TT 不代表没有 XSS，policy 只是把「字符串」变成「被声明为可信的字符串」。
- `el.innerHTML = ''` 不用包装：空字符串被规范显式豁免。

**验证方式（这次最有价值的一招：A/B 对照组）**
光看「修复后正常」不足以证明测试真的覆盖了 bug——可能这个测试页压根没触发 CSP。做法是**生成一个把 `trustedHtml` 改成恒等函数的对照组**（模拟修复前行为），同页同环境跑一遍：
```
control: dockPresent:false ballPresent:false errors:[2× TrustedHTML TypeError]
fixed  : dockPresent:true  ballPresent:true  ballRect 44×44  subLayer:true  errors:[]
```
对照组精确复现了用户描述的故障，修复组零错误——这才叫证明。以后凡是「防御性加固」，都该配一个对照组。

**另一个判断**：`--load-extension` 在无头 Edge 下确实不生效（历史已确认过）。所以扩展侧改用「stub `chrome` API + 把 content.js 当普通 script 注入页面主世界」的方式验证——这比真实情况**更严苛**（真实内容脚本在隔离世界，本就豁免 CSP），过了这一关就没有疑问。



## 字幕只翻译第一条、后续不刷新（用户报「只能翻译刚打开时的字幕，而后不加载不刷新不翻译」）

**根因：同步只挂在 `requestAnimationFrame` 一根绳上。** `startTick` 里 `positionLayer()` 排在 `updateCue()` 前面，只要定位抛一次异常，字幕切换就再也跑不到；rAF 本身在后台标签页会被暂停、在繁忙页面上会被饿死。两种情形都是同一个症状：第一条 cue 由 `updateCue(true)` 直接渲染出来，之后永远不动。

**定位手法（这次的关键）**：之前所有字幕 e2e 都是手动 `dispatchEvent(new Event('seeked'))` 驱动时间轴的——**恰好绕开了 rAF 循环，等于把出问题的那段代码排除在测试之外**。换成「只改 `currentTime`、不发任何事件」再跑，症状立刻复现。教训：测试驱动方式必须和真实路径一致，否则测的是自己写的那套假流程。

顺带发现：**无头 Chromium（`--disable-gpu`、无合成器）里 rAF 根本不触发**，`data-n="0"`。所以以前「e2e 通过」在字幕同步这一项上从来没有真实覆盖过。

**修法（三路驱动 + 故障隔离）**
- `rAF` 负责逐帧平滑；`timeupdate`（约 4 次/秒，rAF 暂停时照常触发）负责推进；再加一个 250ms 看门狗——`Date.now() - lastTick > 150` 就说明 rAF 停了，由定时器接手。三者幂等，因为 `updateCue` 只在 index 真的变化时才重绘。
- `syncOnce()` 里把 `updateCue` 和 `positionLayer` 各自包 try/catch，互不牵连。
- `updateCue` 里 `renderCue` 也包一层：一条坏 cue 不能拖死整条字幕轨。
- **视频元素会被替换**：YouTube 换页/换广告会重建 player，`SUB.video` 变成游离节点后 `currentTime` 永远不变。新增 `ensureVideo()` 每帧校验 `isConnected`，掉了就重新 `findMainVideo()` + 重新绑定。
- **翻译失败不再拆掉整个字幕层**：原来 catch 里 `stopSubtitles() + userOff = true`，一批失败就永久关闭。改成保留原文行、同一 cue 失败两次后标记为「已翻译但为空」停止重试，toast 做 10 秒节流。
- **YouTube 的 `captionTracks` 是异步填充的**：开启字幕时播放器响应可能还没就绪，原来会直接判定「没有可用字幕」并永久放弃。改成 YouTube 上最多重试 3 次（400/800/1200ms）。
- `startSubtitles` 预热窗口从 `ensureTranslated(0)` 改成当前时间点所在 cue——原来从视频中间开启时，翻的是开头那 13 条。

**验证（A/B 同一环境，rAF 全程不触发）**
| | 时间轴表现 |
|---|---|
| 旧代码 | `index` 恒为 0，t=5/9/13 全是第一条 |
| 新代码 | 0 → 1 → 2 → -1，译文逐条跟上 |

故障注入三项（都用 `window.__SUB` 探针观察）：定位每帧抛异常 → 仍推进；中途替换 video 元素 → `swapped: true` 且继续推进；翻译请求全部 reject → 字幕层保留（layers 1）、请求只发 2 次（重试预算生效）。关闭字幕（`Alt+S`）后 `raf: 0 / watchdog: 0 / on: false`，定时器不泄漏。


## 字幕「翻译完一句就停了，原字幕一直停在屏幕上」（第三轮，真正的根因）

**前两次的修复方向都偏了**：第一次加 rAF/timeupdate/看门狗三路驱动，第二次加 ensureVideo 自愈——但都没解决用户反复报告的「只翻译一句就停」。根因不在驱动循环，而在**视频元素选择**。

**真正根因**：`findMainVideo()` 只按「面积最大」挑 `<video>`，完全没看视频是否在播放。YouTube 一页里有多个 video（预览、广告位、迷你播放器、暂停的海报帧）。一旦字幕层绑到了一个**没有在播放**的视频，`currentTime` 就永远不动 → `findCueIndex` 每次返回同一个 index → `updateCue` 直接 `return` → 画面冻在第一句。加载时 `updateCue(true)` 强制渲染第 0 条（恰好 currentTime≈0），之后不动。这精确对应「翻译完一句就停了，原来的字幕一直停在屏幕上，新字幕不显示」。

**修法**：`findMainVideo` 改成**优先选「正在播放」的视频**（`!paused && !ended && readyState >= 2`），面积只在同为播放态时决胜；`ensureVideo` 改成自愈——已绑定的视频若停了/被替换，且页面上有别的正在播放的视频，就切换过去（只在 `next !== current` 时重绑，避免缓冲瞬间抖动）。这把之前写得却从未调用的死代码 `playingVideos()` 用上了。

**这次最有价值的验证手法：对照隔离（A/B 在同一环境）**。直接证明 bug 与修复的因果：
- 造一个页面：一个大尺寸但**暂停**的诱饵视频 + 一个较小但**正在播放**、时间轴前进的视频，两者都挂同一份字幕。
- 从新代码派生一个副本，**只回退** `findMainVideo`/`ensureVideo` 到老逻辑（其余完全一样，含 TT 加固），在带 `require-trusted-types-for 'script'` 的页面跑。
- 结果：老选择逻辑 → 绑到 `poster`、index 恒为 0、字幕冻结（精确复现用户现象）；新逻辑 → 绑到 `player`、index 1→2 推进。
- 扩展侧与用户脚本侧都各跑一遍，结论一致。

**教训**：遇到「只复现不修好」的反复报告，要回到第一性原理找根因，而不是在已有假设上继续打补丁。对照隔离（控制单一变量）比「修复后看起来正常」更有说服力——后者可能只是测试没覆盖到真实路径。

**测试脚手架坑**：后台 `node server.mjs &` 在工具调用之间会被回收，导致后续 curl/页面加载 `ERR_CONNECTION_REFUSED`。必须把「起服务 + 跑浏览器」放进**同一个 shell** 里。另外无头 Chromium 的 rAF 不触发、YouTube 真实播放会话本机无法跑（302 同意页），都用 mock `currentTime` + 派发 `timeupdate`/`play` 来驱动。
